01架构设计与取舍

先说结论：这不是“能跑就行”的 RAG demo，而是一个每一步都可被外部验证的系统。 架构上最大的三个决定——零第三方依赖、真模型本地跑、确定性后端当门禁夹具——都不是技术炫技， 而是被“面试官要在自己的机器上复现”这个约束逼出来的。

1.1 约束即设计

约束如果不这么做的后果因此的系统形态
一份交付物要被陌生人复现 数字只能靠作者口述，评审无法验证 所有指标落盘为快照 + 一条命令重生成；文档与快照有漂移测试
零第三方 Python 依赖 冷克隆可能装不上、版本漂移、CI 不可复现 检索/融合/PDF 抽取/日志全部标准库实现；模型通过 HTTP 调用，不进依赖树
无 API Key 也要能跑 评审拿到仓库却跑不起来 确定性后端（哈希向量 + 特征重排 + 模板生成）作为默认与 CI 夹具
质量要有阈值 “看起来不错”变成验收标准 85 条带标签用例 + 41 行门禁，每条需求指向一个可执行断言

1.3 八个关键决定，以及它们各自反对了什么

决定被拒绝的替代方案为什么在哪里被强制
只用标准库LangChain / FAISS / pandas 冷克隆即可运行是交付底线；依赖越少，"我这儿能跑"与"你能跑"的差距越小 contract-gate 检查无 pip install
模型走 HTTP，不进依赖进程内加载 GGUF 推理与编排解耦：换模型不改代码，模型崩溃不拖垮服务（有健康检查与回退） configs/retrieval.json 的 endpoint

混合检索（BM25 + 向量 + RRF）纯向量 专业术语、编号、缩写靠词面命中；语义靠向量。RRF 不需要两路分数同分布 recall@5 0.7722→0.8987（确定性快照）
重排做成开关永远开启 实测它用召回换排名（recall 0.9615→0.9231，mrr 0.9167→0.9231），并非永远正确 --rerank on|off + 报告结论
两层缓存 + single-flight只做精确缓存 FAQ 型流量重复率高；identical 并发突发如果不合并，会同时击穿缓存打到模型（实测 5 并发 14.1 s → 合并后 3.1 s） 命中率 0.4706 进运维报告
拒绝是显式状态，不是空答案低置信度也硬答 四种 reason code + 引导语，可审计；"答不上来"本身是可测量指标 refusal appropriateness 0.9529
PDF 逐页处理整篇判定是否扫描件 整篇判定会把"1 页文字 + 3 页图片"的文档连同文字一起丢掉；逐页保留可读页并上报无文字页数 tests/test_mixed_scan_pdf.py（R18）
一句话 架构的核心不是"用了什么组件"，而是把"正确"变成可执行断言：需求 → 门禁行 → 测试 → CI job → 规则。 没有测试的承诺在这个仓库里会被当成 bug。

02端到端流程：一条命令 + 一文件夹中英 PDF

场景：评审者把 20 份中英文混合 PDF（含少量纯扫描页、少量图文混排）放进 ./docs-in， 执行 python scripts/run.py --corpus ./docs-in。下面从进程启动开始，逐步到终端输出。

2.1 两张泳道：索引期 vs 查询期

2.2 逐阶段：发生了什么，为什么这样

  1. 进程入口与参数识别scripts/run.py → cli/main.py

    唯一脚本把 argv 交给分发器。分发器按模式旗标选模块；带值的旗标（如 --corpus DIR） 必须与值一起保留——这里曾有过一个 bug：把 --corpus 当无值开关剥掉，路径被留下成为多余参数， 导致 README 里的这条命令 100% 失败。现在由"文档命令即契约"的测试守着。

  2. 环境准备（幂等）cli/setup.py

    按平台选 llama.cpp 资产（win/ubuntu/macos），缺则下载；起 embedding(8011) 与 reranker(8012) 两个进程； 轮询 /health 直到 200（不是等端口监听——模型加载完成前端口就已绑定）。已存在的服务不会重启， 这就是"第二次跑直接干活"的原因。

  3. 语料获取与逐页抽取corpus/loader.py

    遍历目录（或单个文件），按扩展名分流。PDF 走标准库解析：解析 ToUnicode CMap 把 subset CID 映射回 字符（否则中文 PDF 只会抽到控制字符）、把 CMap 流当元数据而非正文、未压缩流原样读。 按页收集文本：有文字层的页入库，纯图片页计入 scanned_pages 并在报告里列出—— 绝不因为"整篇看起来像扫描件"而丢弃可读页。

  4. 清洗、分块与语言判定corpus/builder.py · chunker.py

    目标块长 220 字符、重叠 44；中文信息密度高，按 0.55 系数缩放目标长度，避免中文被切成过短的碎片。 每个块带 doc_id / section / language / ocr 元数据，供检索与降权使用。

  5. 向量化retrieval/embeddings.py

    批量 POST 到 /v1/embeddings（模型 bge-m3，1024 维）。端点不可达时大声回退到确定性哈希向量 （同一份语料两次运行结果一致），并在 provenance 里标 deterministic——绝不把回退说成模型结果。

  6. 建索引retrieval/pipeline.py

    两套索引同时建：BM25 倒排（中英分别分词）与向量矩阵（内存）。同时算出 corpus_version （内容指纹，不含摄取元数据），它进入缓存键与日志，保证"同一问题在语料变化后不会命中旧答案"。

  7. 问题进来先过闸generation/safety.py · pii.py

    注入检测（"ignore previous instructions" 之类）→ 直接拒答并给引导语；问题里的 PII 在入库检索前就脱敏， 避免把用户邮箱写进日志与缓存键。

  8. 多轮改写generation/context.py

    只有当历史存在时才改写：指代（"Can they…?"）与省略式开头（"What about X?" / "那…呢？"）。 首轮永不改写——错误改写比不改写更糟。改写结果在终端显示为 resolved to:，让错误可见。

  9. 缓存与 single-flightcache.py · service.py

    精确层 TTL 300 s，语义层 60 s（token 集合相似度）。同一问题并发到达时，一个 leader 计算，其余等待并共享结果： 实测 5 并发从 14.1 s 降到 3.1 s；命中缓存时约 5 ms。

  10. 混合检索与融合retrieval/pipeline.py

    两路各取 top-20，用 RRF（k=60）融合排名——RRF 只吃名次，不需要把 BM25 分数与余弦相似度归一化到同一尺度， 这是异构检索最稳的融合方式。融合后取前 10 进入重排。

  11. 交叉编码器重排retrieval/rerank.py

    query 与每个候选成对送入 cross-encoder（bge-reranker-v2-m3），得到真实相关性分数后取 top-5。 代价是 0.77 s/次（10 候选，CPU），收益是排名更准——所以它是开关而不是硬编码。

  12. 决策：答、还是拒service.py

    两个可解释信号：coverage（查询词被覆盖的比例）与 confidence（0.6×覆盖 + 0.4×首位分数占比）。 低于 0.08 / 0.30、或没有引用，就返回带 reason code 的拒答（out_of_scope / low_confidence / no_context / safety_trigger / injection_detected）+ 引导语。宁拒不编。

  13. 生成、脱敏、落日志generation/* · observability/events.py

    答案必须带引用；随后对答案与整条日志记录做 PII 脱敏（redact_record 递归处理嵌套结构）。 一次请求发出 5 段结构化事件：request → retrieval → decision → generation → response， 终端把这段延迟打在答案下面。

2.4 同一路径上的边界情况

输入系统行为为什么这样
目录里只有不支持的格式REFUSED: nothing was indexed…，退出码 1，不写报告 0 篇文档还报"成功"，会让评审以为跑过了
路径不存在一行可读错误，退出码 1，无 traceback栈回溯不是给使用者看的东西
纯图片扫描 PDF列入 skipped，报告里注明零依赖下无 OCR；不假装索引成功
图文混排 PDF文字页入库，报告列出"无文字层的页数"整篇丢弃会连带丢掉可读内容
中文 PDF（subset 字体）经 ToUnicode 还原为中文不做这一步抽到的是控制字符，索引里还会混进 "Adobe UCS"
注入式问题拒答 + 引导语，reason=injection_detected在检索前就拦，避免污染上下文

03从“一条命令”到“1,000 并发”：该怎么设计

假设入口从脚本换成 HTTP API，10,000 名注册用户、峰值 1,000 并发。 这一节先讲清楚现在的瓶颈（有测量），再做容量算术，最后给出目标架构与迁移顺序。

3.1 现在的瓶颈在哪（不是猜的）

1 进程ThreadingHTTPServer，会话上限 200；单机单实例
CPU 推理嵌入 0.18 s / 重排 0.77 s，串行排队
内存索引204 块全在进程内；语料变大即受限于单机内存

线程模型本身不慢（I/O 密集），慢的是模型调用与它的串行化： 5 个不同问题并发实测 12.8 s wall，3 个超过 10 s。也就是说，把入口换成 API 而不改这三件事， 1,000 并发会全部堵在模型队列上。

3.2 先做容量算术，再谈组件

用 Little 定律：并发数 C = 吞吐 λ × 单请求耗时 S。反过来，给定 C 与 S 就能算出需要的 λ。

量取值推导
峰值并发1,000题设
目标 p95 端到端≤ 3 s比 10 s 上限留 3× 余量，页面体验才不"卡"
所需吞吐 λ≈ 330 rpsλ = C / S = 1000 / 3 s
缓存命中率0.45–0.60本项目 FAQ 型流量实测 0.4706；命中部分不打模型
真正打到模型≈ 150–180 rpsλ × (1 − 命中率)
检索层 QPS≈ 330缓存未命中 + 命中都要回检索（或缓存直接返回答案）
结论先行 1,000 并发 ≠ 1,000 个模型调用。把缓存、批处理、异步化做对，模型侧只要承接 约 150–180 rps， 这是 2–4 台 GPU 推理节点 + 连续批处理能覆盖的量级；而 API 层是 I/O 等待，扩副本即可。

3.3 目标架构

3.4 为什么是这些组件（而不是“加机器”）

改动解决的具体问题如果不做会怎样
API 层无状态化 会话历史原本在进程内存（cap 200），扩副本后用户会被打到不同实例 多轮对话随机丢上下文；滚动发布时全部会话清零
模型层独立部署 + 连续批处理 嵌入 0.18 s、重排 0.77 s 是串行成本；GPU 上批 32 条与 1 条几乎同价（实测 5 条批量 = 0.18 s） CPU 单实例下 5 个不同问题就要 12.8 s；1,000 并发会排到几分钟
共享缓存（Redis） 现在的缓存在进程内，10 个副本 = 10 份冷缓存，命中率被稀释 10 倍 同样的热门问题在每个副本各打一次模型，成本随副本数线性上升
向量库（HNSW，分片+副本） 204 块可以放内存；百万级不行，且需要独立扩缩与快照 索引重建期间不可用；单机内存成为硬上限
消息队列做摄取 PDF 解析 + 向量化是长任务（CPU 密集），不能占请求线程 上传 200 份 PDF 会打满进程，问答接口一起变慢（噪声邻居）
网关：鉴权 / 配额 / 限流 1,000 并发里必有滥用与爬取；成本与公平性要可计量 一个租户刷爆模型配额，全员变慢；账单无法归因
熔断 + 降级 模型层过载时，宁可返回缓存答案或"降级为抽取式回答"，也不要雪崩 重试风暴把小故障放大成全站不可用
OpenTelemetry（复用 5 段 trace） 现有日志已经是 request→retrieval→decision→generation→response，天然可做分布式追踪 1,000 并发下无法定位"慢在检索还是重排"
不要过早做的两件事 ① 不要先上微服务：这个系统的复杂度集中在"检索质量 + 模型成本"，拆成 12 个服务只会让链路更长； 先把索引与模型拆出去（两个边界）就够。
② 不要先上 Kafka：如果每天只上传几百份文档，SQS/Redis 队列足够；引入 Kafka 的运维成本要能换来吞吐才值得。

3.5 分阶段迁移（按"先解决什么最痛"排序）

阶段做什么预期指标风险控制
P0把服务做成无状态：会话与缓存移出进程（Redis），镜像可水平复制 单机 → 4 副本；缓存命中率维持 ~0.47灰度：先 10% 流量，比较 p95 与拒答率
P1模型层独立：embedding / rerank / LLM 各自部署，开连续批处理 单请求 3 s；模型层承接 150–180 rps双写影子流量，比对答案一致性
P2向量库替换内存索引（HNSW + 副本），保留 BM25 作为并行召回 百万块、p95 检索 < 50 ms保留旧索引回滚路径；按租户分批迁移
P3摄取异步化（对象存储 + 队列 + worker），支持 OCR worker 上传不再阻塞问答；解析可独立扩缩队列积压告警；任务幂等 + 重试上限
P4网关配额/限流、熔断降级、成本看板 单租户故障不影响全局；成本可归因先观测后限流，避免误伤正常用户
这套设计的取舍 它用运维复杂度换可预测的尾延迟与成本。如果流量只有几十并发，更好的选择恰恰是现在这样： 单体 + 内存索引 + 本地模型——因为那时瓶颈不是算力，而是"能不能被复现和验证"。 架构要匹配当前瓶颈，而不是匹配招聘 JD。
